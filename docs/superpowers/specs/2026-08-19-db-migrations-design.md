# Миграции схемы БД

Дата: 2026-08-19. Задача из бэклога: «Миграция базы @backend @feature».

## Контекст

Схема SQLite создаётся при каждом старте через `CREATE TABLE IF NOT EXISTS`
в `backend/app/storage/db/sqlite.go` (`createSchema`). Такой механизм умеет
только заводить таблицы с нуля: изменить существующую прод-базу — добавить
колонку или таблицу — нечем. А такие задачи в бэклоге уже стоят: справочник
упражнений, отметка выполнения тренировки, `Workout.ImageURL`.

## Решение

Версионированные SQL-миграции на `github.com/pressly/goose/v3`,
применяются автоматически на старте приложения.

Почему goose: pure-Go, работает поверх `database/sql` — совместим с
`modernc.org/sqlite`; устоявшийся формат файлов; версии ведёт сам.
Отвергнутые альтернативы: golang-migrate (тяжелее, dirty-флаг при падении
требует ручного вмешательства), своя мини-система (переизобретение того,
что goose уже решил, ради экономии одной лёгкой зависимости).

## Дизайн

### Раскладка

- Миграции — SQL-файлы в `backend/app/storage/db/migrations/`,
  embed'ятся в пакет `db` через `//go:embed migrations/*.sql`
  (тот же паттерн, что у фронта в бинаре).
- Нумерация последовательная: `0001_init.sql`, `0002_...`.
  goose CLI не подключаем, файлы заводим руками.

### Запуск

`NewSqliteEngine`: connect → `setup()` с прагмами (как сейчас) → вместо
`createSchema()` — goose Provider API (`goose.NewProvider(goose.DialectSQLite3, ...)`
+ `provider.Up(ctx)`), без глобального состояния goose. Ошибка миграции —
ошибка старта приложения. После прогона логируем через zerolog, сколько
миграций применено. Версию goose ведёт в таблице `goose_db_version`.

Попутный фикс: сейчас ошибка `engine.setup()` только логируется, но не
возвращается — старт продолжается с недонастроенной базой. Возвращаем её
как ошибку.

### Миграция 0001 и существующие базы

`0001_init.sql` — текущие четыре `CREATE TABLE IF NOT EXISTS` дословно.
На проде таблицы уже есть — миграция пройдёт no-op'ом и зафиксирует
версию 1. Константы схем и `createSchema` из `sqlite.go` удаляются.

Политика up-only: Down-секции не пишем, откат — восстановлением из
бэкапа (задача про бэкапы SQLite стоит в бэклоге отдельно).

Сид и тесты не меняются — схема приезжает тем же `NewSqliteEngine`.

### Тесты

Существующие тесты datastorage/api уже гоняют этот путь через
`testutil.NewEngine` (in-memory; `MaxOpenConns(1)` уже стоит — для
`:memory:` это критично). Добавляем два теста на движок:

1. Повторное открытие одного файла — идемпотентность рестарта.
2. Открытие базы со «старой» схемой (таблицы есть, `goose_db_version`
   нет) — докатывается без ошибок. Это сценарий первого деплоя на прод.

## Вне скоупа

Down-миграции, Go-миграции для данных, goose CLI, смена СУБД.
`schema_version` в таблице workout — версия JSON-пейлоада секций,
к миграциям схемы отношения не имеет.
